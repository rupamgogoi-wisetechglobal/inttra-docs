# Documentation standards

## Required practices

- Use the appropriate file in [`../../templates/`](../../templates/) as the starting point for BRDs, done statements, EDI guides, ADRs, and release notes.
- Give each controlled document an owner, stable identifier where applicable, status, and review date.
- Keep requirements testable and distinguish requirements from design choices and assumptions.
- Link related requirements, specifications, mappings, test plans, and release notes rather than duplicating content.
- Use synthetic examples; never include credentials, customer-identifying data, or production payloads.
- Cite authoritative sources and include the source version or retrieval date for externally maintained code lists and standards.
- Use relative links for repository content.

## Document metadata

Follow the metadata fields in the relevant template. Use ISO 8601 dates (`YYYY-MM-DD`). Update the review date and change history when an approved document changes.

## Identifiers and naming

Use stable, unique identifiers for controlled records. Booking BRDs use `BRD-BKG-0001-<slug>.md`; ADRs use `ADR-NNNN-<slug>.md`. Use lowercase, hyphen-separated names for general files.

## Review and approval

A pull request is the review record. Identify the product, operations, EDI, compliance, architecture, and engineering reviewers needed for the subject. Mark a document `Approved` only after the accountable reviewers have approved its content. Record material changes in the document history and relevant release notes.

## Diagrams and generated output

Keep editable source diagrams (`.drawio` or `.mmd`) in `assets/`. Exported images are supporting artifacts, not the sole source. PDF and DOCX files are generated by the document build workflow and should not be edited as source.
